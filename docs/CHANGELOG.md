### 2026-10-23 (later) — Platform identity foundation: platform company flag, trusted platform context, `[PlatformOnly]` gate

Approved design (platform company + explicit flag + separate gate). **No platform endpoint exists yet; no platform company or administrator was created or designated anywhere** (see docs/PLATFORM_ADMINISTRATION.md).

**Migration `20261023105109_AddCompanyIsPlatform` (not applied to any persistent database).** `Companies.IsPlatform boolean NOT NULL DEFAULT false` and a unique PARTIAL index `IX_Companies_IsPlatform_Single` over the true rows, so at most one company can be the platform company. Generated SQL (read, both directions): `SET LOCAL lock_timeout = '15s'`, `ALTER TABLE "Companies" ADD "IsPlatform" boolean NOT NULL DEFAULT FALSE`, `CREATE UNIQUE INDEX ... WHERE "IsPlatform"`, history row; no UPDATE, so no existing company is designated (metadata-only column add). `Down` drops the index and the column. Tested through the EF runner on throwaway databases: every existing company byte-identical, none designated, only the column and the index added, no physical `xmin` column, rollback restores the exact earlier schema and company data, re-applying designates nobody, the lock timeout does not outlive the migration. Nothing at start-up (migration, either seeder, the Super Admin bootstrap) designates a company (tested).

**Trusted platform context.** `ICurrentUser.IsPlatform`: true only when the caller's company has `IsPlatform` AND exactly one company is designated, computed in the same database round trip that already loads the current user (no extra query, no second context mechanism). Not derived from the token, headers, query, body or role name. Missing or ambiguous designation = false for everyone.

**The gate.** `[PlatformOnly]` (class or action) adds a requirement and grants nothing: the filter requires `ICurrentUser.IsPlatform` AND every `[RequirePermission]`, after the usual authentication, active-account and first-login checks; a failure is the same generic 403. Declaration rule (single `AuthorizationDeclaration.Classify`, used at runtime and by the tests): `[PlatformOnly]` needs a permission and cannot combine with `[AllowAnonymous]`, `[SelfService]` or a bare `[Authorize]` - any such combination is a Conflict denied for everyone, at controller or action level. Runtime backstop: an action under `/api/platform` without `[PlatformOnly]` is refused for everyone. Convention tests require that every production action in that area is gated, every gated action has a permission and lives in the area (trivially true today: no production platform endpoints), and prove the check detects each known mistake in the test-only probe controllers. Employee, department and `GET /api/roles` behavior is unchanged (tested: platform administrator still company-scoped on employees/departments; `GET /api/roles` still works for Super Admins of any company and is still refused for HR).

**Super Admin bootstrap change.** `SuperAdminProvisioner` now creates the account only in the designated platform company (re-read inside its transaction; it must be the one and only designated company); otherwise start-up stops with a message and nothing is created. It never creates or designates a company. All other properties are unchanged (no default password, first-login flag, no promotion of existing accounts, idempotent no-op while any Super Admin exists - including when the settings later name a non-platform company, so a restart never bricks the application - advisory lock, secrets never logged). The 20 existing provisioning tests now designate the scratch company first (standing in for the operator); 5 new ones cover refusal.

**Documentation.** New docs/PLATFORM_ADMINISTRATION.md: the model, a manual designation procedure, bootstrap, audit placement (platform actions are audited in the platform company's audit log; no-actor events stay in `SecurityEvents`), a manual recovery procedure for a locked-out platform administrator (operator-only, two-person, never an endpoint; documented, not executed), operator check queries, and the MFA/network-restriction hardening to plan.

**Tests - 1025 tests, 1025 passed, 0 failed, 0 skipped, twice in a row (was 983).** New: `PlatformGateTests` (22), `PlatformConventionTests` (8), `PlatformDesignationTests` (7), 5 added to `SuperAdminProvisioningTests` (now 25); the migration-list test expects ten migrations. 6 mutation checks killed (platform check removed from the filter, ambiguity not handled, everyone platform, declaration conflicts undetected, area backstop removed, provisioner using an ordinary company). ### 2026-10-23 — Role permission validation and role concurrency foundation (no endpoint)

**Migration `20261023075625_RoleConcurrencyToken` — snapshot-only (not applied to any persistent database).** `Role.Version` (uint) is mapped with `IsRowVersion()` to PostgreSQL's built-in `xmin`, exactly like `Employee.Version`. EF scaffolded `AddColumn "xmin"`; `Up`/`Down` were emptied on purpose (a physical column named xmin must never be created), documented in the file. Generated SQL (read): only the `__EFMigrationsHistory` insert. The model snapshot maps Role.Version to `xmin`; `has-pending-model-changes`: none; nine migrations. Tested through the EF runner on throwaway databases holding roles: schema and every role identical before/after, no `xmin` column in `information_schema`, `xmin` readable on every row, rollback and re-apply harmless.

**Write-side validator `RolePermissionValidator`** (Application/Features/Roles; `Validate(string)`, `Validate(JsonElement)`, FluentValidation rule `ValidRolePermissions()`). Returns `PermissionDocumentResult` = errors (`Path`, `Code`, `Message`) or, when valid, the permissions and the canonical JSON. It uses the one existing `PermissionCatalog` and the existing serializer `RolePermissions.ToJson`; nothing was duplicated, and the read-side `RolePermissions.Parse` is unchanged (still drops what it does not recognise; a test shows the two side by side). Rules: valid JSON without comments or trailing commas, depth at most 4; root must be an object (`{}` is allowed: a role with no permissions); every module and action must be in the catalog, compared ordinally and case-sensitively (no trimming, case folding, culture or coercion; look-alike Unicode letters rejected); a module is a NON-EMPTY array of strings (a module that grants nothing is omitted, never sent empty); no duplicate module (repeated JSON key) or action; one bad entry rejects the whole document, nothing is dropped or repaired. Limits (assumptions; the specification sets none): 16 KiB (bytes), 64 modules, 64 actions per module, at most 50 errors reported. Untrusted names are echoed truncated and without control characters; malformed JSON is never echoed. Defect found by the tests and fixed: with more than 64 modules the error cap hid the "too many modules" error; the count is now checked first.

**Built-in role invariants `SystemRoleInvariants`** (Domain/Authorization; `Validate` on all four roles, `ValidateChange(roleKey, proposed, current)`). Derived from the catalog and the order in `SystemRoleKeys.All`: every role present and holding only catalog permissions; hierarchy employee ⊆ manager ⊆ hr_admin ⊆ super_admin; `super_admin` keeps `roles.view` and `roles.manage_permissions`; no lower built-in role may hold any `roles` permission (specification matrix: role management is Super Admin only). The shipped definitions satisfy all of it, so no role row or seed was changed. Custom company roles are not covered (their limits depend on who edits them - a later decision).

**Concurrency in use:** `IRoleRepository` / `RoleRepository` (same visibility as `GET /api/roles`: built-in roles and the caller's own company's roles; fails closed without a resolved user). `SaveChangesAsync` translates ONLY `DbUpdateConcurrencyException` into the new `ConcurrencyConflictException` (a `ConflictException`, so the existing 409 mapping applies, but a handler can tell it apart); every other failure (invalid jsonb, unique index, cancellation) surfaces unchanged. A role deleted meanwhile is also reported as a conflict.

**Not done on purpose:** no `PUT /api/roles/{id}/permissions` or any write endpoint (a test still pins that no write route exists), no role assignment, no custom-role CRUD, no new permission for any role, no tenant or Super Admin change, no ETag/If-Match on roles (needs the endpoint).

### 2026-10-22 (later) — Super Admin provisioning (explicit bootstrap, company-scoped)

**No migration, no schema change, no change to authorization, tenant resolution, login or the permission catalog** (eight migrations; `has-pending-model-changes`: none).

**`SuperAdminProvisioner`** runs at start-up after the seeders (Development and Production only; the Testing environment runs neither) and is OFF unless configured. Settings (environment variables / configuration; all three required together, otherwise start-up stops with a message naming the missing setting): `HRMS_SUPERADMIN_EMAIL`, `HRMS_SUPERADMIN_PASSWORD`, `HRMS_SUPERADMIN_TENANT_DOMAIN` (an EXISTING active company; none is ever created); optional `HRMS_SUPERADMIN_NAME` (default "Super Administrator"). Behavior:
- creates one user with the shared `super_admin` system role in that company, active, **IsFirstLogin = true** (the configured password is temporary: login works, everything else is refused until the existing change-password flow is used);
- the password has no default, must meet the normal password policy (12+ characters, at most 72 bytes, no control characters) and must not equal the e-mail; it is BCrypt-hashed and never logged, echoed or placed in an error;
- creates NOTHING while any Super Admin exists anywhere (a rerun is a no-op; a different configuration is ignored with a warning; a deactivated Super Admin is not recreated by a leftover setting);
- never promotes an existing account: if the configured e-mail already belongs to a user of the company, start-up stops (the message names the existing role key, not the e-mail) and nothing changes;
- one transaction under a PostgreSQL advisory lock, so concurrent starts create at most one account (tested with 8 parallel runs);
- records a `platform.super_admin_provisioned` row in `SecurityEvents` (user = the new account; the audit log needs an acting user and the bootstrap has none, so no actor is invented);
- logs only ids; after the first successful sign-in and password change the password setting should be removed.
**What this is NOT:** it creates no platform-level identity. The account is an ordinary user of the configured company with the `super_admin` role: same company-only data scope as HR Admin plus `roles.view`/`roles.manage_permissions`, signs in only on that company's host, and a token is refused on any other company's host. Platform privileges are not inferred from the role name or a JWT claim (permissions are read from the database; a token claiming `super_admin` for an HR account gets 403 on `GET /api/roles`). D2 stays open; the choice of the hosting company is an explicit setting precisely so that it can be revisited.
**Tests - 903 tests, 903 passed, 0 failed, 0 skipped, twice in a row (was 881).** New: `SuperAdminProvisioningTests` (20 cases, each in a fresh scratch database) and `SuperAdminBoundaryTests` (2). Covered: first run, exact stored state, no change to other rows, rerun, other configuration ignored, deactivated account kept, HR Admin not promoted, off/partial/invalid configuration (e-mail, password policy, length, e-mail-as-password, name), unknown/inactive company, parallel starts, end-to-end sign-in (wrong and guessable passwords refused, first-login restriction, change password, roles listing, no access to another company's employees/departments, token refused on another host), HR cannot use role management or create a Super Admin, role fields in an employee request are ignored, no API route provisions or promotes. 7 mutation checks killed (existing-Super-Admin check, advisory lock, promotion guard, first-login flag, password policy, security event, unknown company). Not tested: the `Program.cs` start-up call itself (the Testing host does not run seeders).

### 2026-10-22 (later) — Roles API, read-only: GET /api/roles

**No migration, no schema or authorization change** (eight migrations; `has-pending-model-changes`: none). Read-only: no write route exists (a test pins that POST/PUT/DELETE on roles and the role-assignment route answer 404/405).

**`GET /api/roles`** (specification API table: "List all roles and their permissions", Super Admin). Requires authentication and the existing catalog permission `roles.view`, which only the built-in `super_admin` role holds; a role with only `roles.manage_permissions` is refused. Response 200: `RoleDto[]` = `{id, key, displayName, isSystem, scope, permissions}`; `permissions` is a JSON object (module -> actions, canonical order), not an escaped string. Errors: 401 unauthenticated, 403 missing permission / deactivated account / role of another company / password change pending. No company id, timestamps or user data are exposed.
**Scope (smallest safe design, D2 untouched):** the four built-in roles (`scope = "system"`: company-less and flagged system - shared by ALL companies, so the response says so) first in hierarchy order, then the caller's OWN company's custom roles (`scope = "company"`) by name. Another company's roles are never returned; no company parameter or header is read; the company comes only from the authenticated user. A role with no company that is not flagged system is ignored (fail closed). One query; no cross-company bypass and no change to the employee/department scope.
**Permissions** go through the existing strict parser: malformed shapes (array root, string/number values, scalars, null), unknown modules and unknown actions grant nothing and are not reported; stored values are never rewritten.

### 2026-10-22 (later) — Departments completed: delete and bulk employee reassignment

**No migration** (still eight; `has-pending-model-changes`: none). Both operations rely on constraints that already exist.

**`DELETE /api/departments/{id}`** (`departments.manage`; approved rule): allowed only when no employee record (any status) is assigned and no department is nested under it. 204 on success; 404 for a missing or other-company department (identical body); 409 when employees or sub-departments exist (nothing is cascaded or moved); 401/403 as usual. Audited as `department.deleted` (old state = name/parent/head, new = null) in the same transaction; a rejected or failed delete writes no audit row. **Race safety is enforced by the database, not by the application's counts:** `Employees.DepartmentId` and `Departments.ParentDeptId` are RESTRICT foreign keys, so an employee assigned or a child created concurrently makes PostgreSQL refuse the DELETE (or the other insert/update), the transaction rolls back and the answer is 409 (proven with an uncommitted row on a second connection; with the counts removed the tests still pass). The delete also takes the company's hierarchy lock, so deletes and re-parentings of one company are serialized.

**`POST /api/departments/{id}/reassign-employees`** (`departments.manage`, no new permission; {id} = source department). Request `ReassignEmployeesRequest` = `{toDepartmentId, employeeIds[]}`; response `ReassignEmployeesResponse` = `{fromDepartmentId, toDepartmentId, reassignedCount, employeeIds[]}` (200). 404 unknown/foreign source; 400 for: destination missing or foreign (same answer), destination = source, list missing/empty/over 500/with an empty id/with duplicates, any employee missing or in another company (same answer), any employee not currently in the source department; 409 when an employee was changed concurrently. Everything is validated before anything is changed; the moves and one `employee.department_changed` audit entry per employee (old `{departmentId}`, new `{departmentId}` and nothing else) are saved in ONE transaction, so a failure leaves every employee where it was. Offboarded employees can be moved (otherwise a department could never be emptied). The 500 cap is a safety assumption. Concurrent edits are caught by the employees' `xmin` token: a second reassignment of the same employees, or an edit committed meanwhile, fails the whole save with 409 (tested with a locked row and with two parallel requests: all employees always end in one place and the audit count equals the moves that happened).

**Existing tests changed deliberately:** the test that pinned "DELETE answers 405" was replaced by the delete tests; the Swagger test now expects `delete` and `reassign-employees` to exist.
**Tests - 864 tests, 864 passed, 0 failed, 0 skipped, twice in a row (was 845).** New: `DepartmentDeleteAndReassignTests` (20 cases). 9 mutation checks, all killed and restored (source membership, tenant binding of the employee lookup, destination check, audit old value, duplicate rule, same-source rule, race-time error mapping, missing save, and the validator message for duplicates); removing the application's own counts is deliberately NOT detectable by the HTTP tests because the foreign keys give the same 409 (verified: 48 department tests still pass without them).

### 2026-10-22 — Departments module (Phase 1, section 5.3)

**No migration.** The `Departments` table already holds everything Table 5 defines (`Name varchar(100)`, nullable `HeadEmpId` and `ParentDeptId` foreign keys, `CompanyId`, `CreatedAt`); `dotnet ef migrations has-pending-model-changes` reports none and the eight migrations are unchanged. No database was touched outside the guarded Testcontainers instance.

**Endpoints** (`/api/departments`, DTOs only, no entity exposed): `GET` list and `GET /{id}` need `departments.view_own_department`; `POST` and `PUT /{id}` need `departments.manage`. Requests: `CreateDepartmentRequest` / `UpdateDepartmentRequest` = `{name, parentDepartmentId?, headEmployeeId?}` (PUT replaces all three, null clears parent/head). Response `DepartmentDto` = id, name, parentDepartmentId/Name, headEmployeeId/Name, employeeCount (every assigned record whatever its status), childDepartmentCount, createdAt - no company id. 201 + Location on create; 400 validation / cross-company or missing reference / cycle; 401; 403; 404 (missing, other company and out of scope are indistinguishable); 409 only for a database conflict.

**Scope** (API table: "HR: all; Manager: own dept"), added to the existing `IDataScopeService`: `departments.view_all` = the caller's company; otherwise `view_own_department` = only the department of the caller's own employee record (an account without one sees nothing). Every query is bounded by the caller's company first. The filter takes one permission per action, so GET requires `view_own_department`, which every approved system role holding `view_all` also holds; a custom role with `view_all` alone is denied (fail closed).

**Rules:** name 1-100 characters, trimmed, no NUL; parent and head must belong to the caller's company (same 400 whether missing or foreign); a department cannot be nested under itself or a descendant (depth unlimited, bounded walk fails closed); re-parenting is serialized per company with a PostgreSQL advisory lock (two-key form, separate key space from the employee-code lock) so two concurrent moves cannot together create a cycle; the head must not be inactive unless it is the head the department already has (assumption, as for managers); the head need not belong to the department; repeated names are allowed (the specification defines no uniqueness).

**Audit/transactions:** `department.created` and `department.updated` are `IAuditedRequest`s with `[AuditExpectation]`; entries carry actor, company and IP from trusted context and the business fields only (update has before and after). A failing audit entry rolls the change back (tested).

### 2026-10-21 — Onboarding reliability and authentication hardening: transactional invitation outbox, rate limiting, security events, trusted-proxy policy

(Date note: the machine clock and the migration timestamps say 2026-10-21; the headings of the entries below this one carry later dates, which was an inconsistency of earlier sessions and was not rewritten.)

**Migration `20261021143131_AddOutboxAndSecurityEvents` (not applied to any persistent database).** Purely additive: two new tables and nothing else. `OutboxMessages` (Id, CompanyId, Kind, UserId, SetupTokenId, Status, Attempts, NextAttemptAt, LockedUntil, ProcessedAt, `LastError varchar(100)`, CreatedAt; RESTRICT foreign keys to Companies, Users and AccountSetupTokens; **unique index on SetupTokenId** = the idempotency key; index (Status, NextAttemptAt) for the claim query; checks `Status IN ('Pending','Processing','Sent','Failed','Cancelled')` and `Attempts >= 0`) and `SecurityEvents` (Id, CompanyId, **nullable** UserId, EventType, Reason, IpAddress varchar(45), CreatedAt; RESTRICT foreign keys; indexes (CompanyId, CreatedAt) and (UserId, CreatedAt)). Starts with `SET LOCAL lock_timeout = '15s'`. Generated SQL read (script from the previous migration): `START TRANSACTION`, the `SET LOCAL`, two `CREATE TABLE`, six `CREATE INDEX`, the history row, `COMMIT`; no existing table, column or row is touched and no message is invented for tokens issued before it. Tested through the EF migration runner on throwaway databases in the guarded Testcontainers instance (`OutboxMigrationTests`, 5): existing rows and schema unchanged, exactly the documented objects added, no column could hold a token/address/payload, unique/check/foreign-key rules enforced, a token with a pending message and a user with a security event cannot be deleted, rollback returns the exact earlier schema, re-apply works, the lock-timeout setting does not outlive the migration. Also read again this session (no change): `20261021122048_EmployeeConcurrencyToken` is still snapshot-only (generated SQL = only the history row; no `xmin` column anywhere) and `20261021130210_...` is purely additive (nullable columns without defaults, one table, three indexes; `TokenHash varchar(64)` fits SHA-256 hex).

**1. Transactional outbox for invitations (replaces "send inside the request after the commit, no retry").**
- `AccountInvitationIssuer` now writes, inside the creating transaction, the `AccountSetupToken` (hash of a throw-away random value that nobody ever sees) and an `OutboxMessage`. A rolled-back transaction leaves neither, so nothing deliverable exists for it. After the commit `IInvitationDispatcher.NudgeAsync` makes one immediate attempt (`Outbox:InlineDelivery`, default on); the hosted `OutboxWorker` (default on, polls every 15 s) retries.
- **How delivery works with hash-only storage (decision, threat model in DEVELOPMENT_LOG Session 25).** The outbox row holds no secret. At delivery the processor generates the raw token, replaces the hash of the pending token row with its hash (only if the row is still open and unexpired; the promised expiry never moves), and sends outside any transaction. So reading the database never yields a usable credential and no encryption key has to exist.
- Claiming: one `UPDATE ... WHERE Id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING`, with a lease (default 2 min) and the attempt counter incremented at claim; a dead worker's claim is taken over after the lease. Concurrent workers deliver a message once; a state change is guarded by (status, attempt number) so a worker that lost its lease cannot overwrite the new owner's result.
- Failure policy (`Outbox` section): `MaxAttempts` 6, delay `BaseDelay` 30 s × 2^(attempt-1) capped at `MaxDelay` 1 h (30, 60, 120, 240, 480 s between the six attempts: terminal about 15.5 minutes after creation), then `Failed` (terminal, logged at error level with the message and user ids, never retried). `Cancelled` (terminal) when the account no longer needs it (inactive, already set up), the token was consumed/revoked/replaced or has expired. A claim that expired with the attempts used up becomes `Failed` ("abandoned"). While `IAccountInvitationSender.IsConfigured` is false nothing is claimed and no attempt is burned. Shutdown during a send returns the message without costing an attempt.
- Observability: `Status/Attempts/NextAttemptAt/LastError` in the table; warnings per failed attempt and an error per terminal failure, all with message id, attempt and **exception type only** (a message could contain the recipient or a secret); no token, hash or address in any log, audit entry or row (tested across all tables).
- Delivery is **at-least-once**: if the process dies after the channel accepted a message but before the status was written, the message is sent again with a newer token and the older link stops working.
- A pre-existing latent problem the redesign exposed and the tests now pin: two tokens created in the same instant (frozen test clock) were returned in arbitrary order by `ORDER BY CreatedAt`; the re-issue test now advances the clock between the two invitations.

**2. Rate limiting (ASP.NET Core rate limiter + a small in-memory attempt limiter; all limits configurable, section `RateLimiting`, `Enabled`).** Endpoints opt in with `[AuthRateLimit(policy)]` (a test pins exactly four: login, set-password, change-password, invitation re-issue). One chained global limiter applies fixed windows: login 20 per 60 s per client address; set-password 10 per 60 s per address; change-password 30 per 60 s per address; re-issue 60 per 60 s per address. Per identity: change-password 10 per 900 s **per authenticated user**; re-issue 30 per 3600 s per administrator and 5 per 3600 s per target employee. Body-keyed budgets (`AttemptLimiter`): login 10 per 300 s per **(tenant, client address, normalized e-mail)**, identical whether the account exists or not (no oracle); set-password 10 per 900 s per token (hashed key). An account budget always includes the caller's own address, so someone elsewhere cannot exhaust a victim's budget, and every window ends by itself (no permanent lockout). IPv6 clients are keyed by /64. Rejections are one 429 shape (`{"message":"Too many requests. Please try again later."}`, integer `Retry-After`) from both mechanisms, are logged as a warning (method and path only), and happen before any database work (no security event is written for them). Counters live in memory per application instance.

**Client address / reverse proxy (`ForwardedHeaders` section).** Forwarded headers are **not trusted by default**: the address is the TCP peer, so it cannot be chosen by a caller (`X-Forwarded-For` is ignored; tested). A deployment behind a proxy must set `ForwardedHeaders:Enabled=true` and list `KnownProxies` and/or `KnownNetworks` (CIDR); only headers sent by those peers are used and `ForwardLimit` (default 1) reads one entry from the right, so entries a client prepended are ignored. Enabling it without naming a proxy, or with a malformed address, stops the application at start. `TrustAllProxies=true` exists for platforms whose load balancer overwrites the header and cannot be bypassed; it must be a conscious choice. Both the rate limiter and the audit/session/security-event address read the same corrected value. **Until this is configured behind Render, every user shares the proxy's address and therefore one per-address budget.**

**3. Security events for rejected password operations.** New append-only table `SecurityEvents` (own connection, so the record survives the command's rollback; a write failure is logged by type and never changes the response). Recorded: `auth.set_password_failed` (reasons `invalid_token` for unknown/expired/used/replaced/foreign-tenant tokens, `account_not_eligible` for a valid token whose account is deactivated or already set up) and `auth.change_password_failed` (`wrong_current_password`). ### 2026-10-23 — Transaction pattern for data-changing handlers (no migration)

**Why:** the audit review found that `Stage` only adds the row to the request's DbContext, so with several `SaveChanges` calls (repositories save by themselves) or an immediate bulk update, an audit row could commit with only part of an operation, or a change could commit without its audit row. No transaction code or MediatR transaction behavior existed (`BeginTransaction` appeared nowhere; `ValidationBehavior` was the only pipeline behavior).

**Mechanism**
- `ITransactionalRequest` (marker) and `IAuditedRequest : ITransactionalRequest` (marker) in `HRMS.Application/Common/Transactions`. A command opts in by implementing one of them.
- `TransactionBehavior<TRequest,TResponse>` (MediatR), registered **after** `ValidationBehavior` in `Program.cs`, so invalid requests are rejected before a transaction opens. Requests without a marker (queries, login, logout, me) pass straight through - no transaction.
- `IUnitOfWork.ExecuteAsync` implemented by `EfUnitOfWork` on the request's `HrmsDbContext`: opens one explicit transaction, runs the handler, flushes pending changes **inside** the transaction (`SaveChangesAsync`), commits once. Any exception or cancellation rolls back (non-cancellable rollback, original exception rethrown unchanged) and clears the change tracker, so rolled-back entities and staged audit rows are not left "pending" in the context. If a transaction is already open (a handler sent another transactional request, or the caller opened one) it **joins** it and never commits or rolls it back (no nesting, no double commit). Uses the provider's execution strategy (non-retrying for Npgsql today).
- Repositories keep calling `SaveChanges` themselves: inside the unit of work those saves, and `ExecuteUpdate/ExecuteDelete`, run on the transaction's connection and are invisible to other connections until the single final commit.

### 2026-10-21 — Security fix: class-level `[AllowAnonymous]` could disable `[RequirePermission]` (no migration)

**Defect (found by the read-only verification of the authorization foundation):** `PermissionAuthorizationFilter` returned immediately when the endpoint metadata contained any `IAllowAnonymous`. ASP.NET Core also lets `[AllowAnonymous]` skip the authentication requirement of `[Authorize]`-derived attributes, so a controller marked `[AllowAnonymous]` made an action's `[RequirePermission]` (or `[SelfService]`) unreachable-by-design yet reachable in fact: an anonymous caller, or an authenticated user without the permission, received 200. The convention test accepted that combination. No production controller had it (`AuthController`: login anonymous, logout/me self-service; `HealthController`: anonymous), so this was a latent defect, not an exploited one.

**Fix**
- New `HRMS.API/Authorization/AuthorizationDeclaration.cs`: one rule, `Classify(metadata)` → `Undeclared | Anonymous | Protected | Conflict`. `[AllowAnonymous]` is honoured only when it stands alone; next to `[RequirePermission]`, `[SelfService]` or a bare `[Authorize]` (at controller or action level, in either order) it is a **Conflict**; `[RequirePermission]` together with `[SelfService]` is also a Conflict.
- `PermissionAuthorizationFilter`: uses `Classify`; Conflict → 403 for everyone (even a user who holds the permission), Anonymous → pass, Undeclared → 401 unauthenticated / 403 authenticated (unchanged), Protected → unchanged flow.
- There is no `[RequireAuthenticatedUser]` attribute in the code base; `[SelfService]` is the authenticated-only declaration.
- Unchanged: permission catalog, role grants, JWT, sessions, tenant resolution, migrations.

**Tests (disposable Testcontainers only) — 355 tests, 355 passed, 0 failed, 0 skipped (was 328)**

**Database schema changes the migration makes** (Up)

- Converted to `jsonb` with explicit `USING col::jsonb`: `Roles.Permissions`, `AuditLogs.OldValue`, `AuditLogs.NewValue`.

### 2026-10-05 — Authentication hardening (no database schema change, no migration)

**Added**
- `HRMS.API/Middleware/ExceptionHandlingMiddleware.cs`, registered first in the pipeline. Maps `FluentValidation.ValidationException` → 400 (field errors), `UnauthorizedAccessException` → 401, `ForbiddenException` → 403, anything else → 500 with a generic message (logged server-side, no stack trace in the response).
- `HRMS.Application/Common/Exceptions/ForbiddenException.cs`.
- Session enforcement: the JWT bearer `OnTokenValidated` event (`Program.cs`) rejects the request (401) unless a Session row exists with `TokenHash` = SHA-256 of the presented bearer token and `ExpiresAt` in the future. Existing JWT signature, issuer, audience and lifetime validation unchanged. No second token/session mechanism; raw JWTs are not stored.
- `POST /api/auth/logout` (authenticated): deletes the Session row matching the current token's hash. Only the current session is removed; idempotent.
- `HRMS.Application/Features/Auth/Commands/Logout/` (`LogoutCommand`, `LogoutCommandHandler`).
- Login session metadata: `Session.IpAddress` and `Session.UserAgent` are now recorded via `IClientInfo` (`HRMS.Application/Interfaces/IClientInfo.cs`) implemented by `HRMS.API/Services/HttpClientInfo.cs` (user agent capped at 512 characters).
- `HRMS.API/Extensions/HttpRequestExtensions.cs` (`GetBearerToken`).
- FluentValidation: `LoginCommandValidator` (email required/valid/≤255, password required/≤128); `HRMS.Application/Common/Behaviors/ValidationBehavior.cs` registered as a MediatR open behavior; validators auto-registered from the Application assembly.
